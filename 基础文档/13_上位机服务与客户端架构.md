# 13 · 上位机服务与客户端架构

> 项目：ESP32-S3 两轮差速 ROS2 智能小车
> 文档版本：**v1.0**　｜　正式发布版
> 生成日期：2026-11-07
> 适用范围：L2 服务层 + L3 客户端层（不涉及 ESP32 固件）

---

## 1. 本文档解决什么

前 12 份文档解决的是"设备怎么接、固件怎么写"。本文档解决三件新事：

1. **Windows 端的 Web 操作界面**（浏览器打开就能开）
2. **安卓端操作端**（优先 HTML/PWA，不做原生 APP）
3. **公网远程控制 + 远程视频**（人在外面也能开）

这三件事共同要求一件事：**在上位机上加一层"服务层"**，把 ROS2 内部的东西翻译成浏览器/手机能懂的东西。

## 2. 三层架构

### 2.1 总图

```
┌─────────────────────── L3 客户端层 ───────────────────────┐
│   Windows 浏览器        Android 浏览器 / PWA               │
│   (Chrome/Edge)         (Chrome / 添加到桌面)              │
└────────────┬──────────────────────┬──────────────────────┘
             │ wss / https          │ wss / https
             │ （局域网直连 或 公网隧道）
┌────────────┴──────────────────────┴──────────────────────┐
│              L2 服务层（WSL2 · Ubuntu 22.04）              │
│                                                          │
│  ┌────────────────────┐   ┌──────────────────────────┐   │
│  │  ROS2 图            │   │  web_gateway (FastAPI)   │   │
│  │  /scan /odom /imu   │◄─►│  REST + WebSocket        │   │
│  │  /cmd_vel /map      │   │  同时是一个 rclpy 节点     │   │
│  │  slam_toolbox/Nav2  │   │  静态托管 SPA             │   │
│  └─────────▲──────────┘   └──────────────────────────┘   │
│            │ UDP 8888/8889/8891/8892                      │
└────────────┼─────────────────────────────────────────────┘
             │
┌────────────┴─────────────────────────────────────────────┐
│                  L1 设备层（ESP32-S3 × 3）                 │
│  板1 主控   板2 感知   板3 音频                            │
└──────────────────────────────────────────────────────────┘
```

### 2.2 两条协议平面（**不要混**）

| 平面 | 链路 | 协议 | 谁懂 | 特点 |
|---|---|---|---|---|
| **L1 设备面** | ESP32 ↔ 上位机 | **X-Protocol / UDP** | 只有固件和 ROS2 桥接节点 | 二进制、极简、低延迟 |
| **L2 客户面** | 上位机 ↔ 浏览器/手机 | **JSON / WebSocket + REST** | 前端 | 可读、可调试、跨平台 |

> 🔴 **绝对不要把 X-Protocol 直接暴露给浏览器**。浏览器做不了 UDP，也不该知道帧结构。中间那层 `web_gateway` 就是翻译官。

### 2.3 为什么加这一层，而不是让前端直连 ROS2

| 方案 | 问题 |
|---|---|
| 浏览器直连 DDS | 浏览器没有 DDS 实现；且 DDS 是组播，跨网段就废 |
| 用 rosbridge_suite | 可行，但图像走 base64 膨胀 33%，且前端仍要自己写 UI |
| **自建 web_gateway** | ✅ 数据可裁剪（10Hz 而非 50Hz）、图像二进制直通、鉴权可控、可加业务逻辑 |

## 3. 上位机进程模型

### 3.1 进程划分

```
进程 A：ROS2 栈
  ros2 launch robot_bringup bringup.launch.py
    ├─ device_io        UDP 8888 ↔ /cmd_vel /odom /imu /battery /servo
    ├─ lidar_bridge     UDP 8889 → /scan
    ├─ cam_bridge       UDP 8891 → /image_raw/compressed
    ├─ audio_bridge     UDP 8892 ↔ /audio/in /audio/out
    ├─ robot_state_publisher  (URDF → /tf)
    ├─ slam_toolbox
    └─ nav2_bringup

进程 B：web_gateway
  uvicorn gateway:app --host 0.0.0.0 --port 8080
    ├─ 内部起一个 rclpy 节点（后台线程 + MultiThreadedExecutor）
    ├─ 订阅 /odom /imu /battery /scan /image_raw/compressed
    ├─ 发布 /cmd_vel /initialpose /goal_pose
    └─ 托管前端静态文件
```

> **为什么不把 gateway 塞进 ROS2 launch？** 可以塞，但独立进程能单独重启、单独看日志、崩溃不影响导航。代价是两者靠 ROS2 话题通信（天然解耦）。

### 3.2 线程模型（gateway 内部）

| 线程 | 职责 |
|---|---|
| 主线程 | uvicorn 事件循环（asyncio） |
| `ros_spin` | `rclpy.spin(node)`，MultiThreadedExecutor |
| `ws_broadcast` | 定时从"最新值缓存"取数据推给所有 WS 客户端 |

**关键点**：ROS2 回调**不要**直接 `await ws.send()`。做法是回调只更新一个 `latest_state` 字典（加锁），广播线程按固定频率（10Hz）读一次推出去。这样 50Hz 的 `/odom` 不会把前端淹掉。

## 4. Web 网关设计

### 4.1 REST 接口

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/auth/login` | 用户名密码 → JWT |
| POST | `/api/auth/refresh` | 刷新 token |
| GET | `/api/status` | 一次性拉全量状态（首屏用） |
| POST | `/api/mode` | 切换 MANUAL / SLAM / NAV |
| POST | `/api/estop` | **急停（最高优先级）** |
| POST | `/api/nav/goal` | `{x, y, theta}` 导航目标 |
| POST | `/api/nav/cancel` | 取消导航 |
| GET | `/api/map` | 当前地图（PNG，可选叠加机器人位姿） |
| POST | `/api/map/save` | 保存地图到磁盘 |
| POST | `/api/camera` | 设置分辨率/帧率/开关 |
| POST | `/api/servo` | 云台角度 |
| GET | `/api/logs` | 最近 N 条日志 |

> FastAPI 自动生成 `/docs`（Swagger UI），**这份 OpenAPI 就是 L2 接口契约**，直接进 SDD 规格库。

### 4.2 WebSocket 通道（**分开四条，不要合一条**）

| 通道 | 方向 | 格式 | 频率 | 用途 |
|---|---|---|---|---|
| `/ws/telemetry` | S→C | JSON | 10Hz | 位姿、IMU、电量、系统状态 |
| `/ws/control` | C→S | JSON | 20Hz | 速度指令、云台、心跳 |
| `/ws/scan` | S→C | JSON | 5Hz | 降采样点云（画小地图） |
| `/ws/video` | S→C | **二进制** | 10fps | JPEG 帧 |

**为什么分开**：视频是连续大包，如果和 JSON 混在一条通道里，会阻塞控制/遥测（队头阻塞）。分开后视频卡了不影响遥测。

### 4.3 遥测消息 schema

```json
{
  "t": "state",
  "ts": 1730000000123,
  "odom": { "x": 1.234, "y": 0.456, "th": 1.57, "vx": 0.30, "vw": 0.10 },
  "imu":  { "roll": 0.5, "pitch": -1.2, "yaw": 89.7 },
  "batt": { "v": 7.82, "i": 650, "soc": 72 },
  "sys":  {
    "mode": "MANUAL",
    "faults": 0,
    "rssi": -55,
    "boards": { "1": true, "2": true, "3": false },
    "uptime": 3621
  }
}
```

**裁剪原则**：前端只显示 2 位小数，`/odom` 的协方差、`/imu` 的四元数都不下发（前端不需要）。**能少发就少发**，WiFi 是共享资源。

### 4.4 控制消息 schema

```json
{ "t": "cmd", "ts": 1730000000123, "vx": 0.30, "vw": 0.00, "seq": 1234 }
```

| 字段 | 约束 |
|---|---|
| `vx` | -0.6 ~ +0.6 m/s（服务端二次限幅） |
| `vw` | -3.0 ~ +3.0 rad/s |
| `seq` | 单调递增，服务端丢弃乱序包 |
| 频率 | 前端固定 20Hz 发送（**不是"有变化才发"**） |

#### ⚠️ L2 的 `seq` 与 L1 的 `seq` 是两回事

系统里有**两个独立的序号**，不要混用：

| 层 | 位置 | 类型 | 作用域 | 谁生成 |
|---|---|---|---|---|
| **L2** | 这条 JSON 的 `seq` | `uint32` | 浏览器 ↔ `web_gateway`（WebSocket） | 前端 |
| **L1** | `0x50` 帧的 `DATA[0]` | `uint8` | `web_gateway` ↔ 板 1（UDP） | gateway |

两者的用途相同（丢弃乱序旧包），但**作用域完全不同**：

```
浏览器 ──[L2 seq: uint32]──► web_gateway ──[L1 seq: uint8]──► 板1
                                    │
                                    └─ 翻译时丢弃 L2 seq，重新生成 L1 seq
                                        （L2 的 uint32 塞不进 L1 的 1 字节）
```

**`web_gateway` 的转发规则：**

1. 收到 L2 `cmd`，先按 `uint32` 判新旧，旧包直接丢弃
2. 通过校验后，用**自己的** `uint8` 计数器（`0~255` 循环）作为 `0x50` 的 `seq`
3. **不要把 L2 的 seq 截断成低 8 位**——`1234` 和 `1234+256` 低 8 位相同，会被板 1 误判为重复包

> 板 1 侧只认 L1 seq，规则见 `00` §5.4：`(int8_t)(in - last) > 0` 才接受。

### 4.5 死手开关（Deadman）——**必须有**

```
前端：每 50ms 发一次 cmd（哪怕速度是 0）
服务端：维护 last_cmd_ts
        if (now - last_cmd_ts > 500ms) → 发布 /cmd_vel = 0，并置 DEADMAN 标志
        if (now - last_cmd_ts > 2000ms) → 判定客户端掉线，广播给其他客户端
```

> 这一条是**公网遥控的生命线**。没有它，网络一卡，车就以最后的速度一直冲出去。

### 4.6 点云降采样

ESP32 每圈 400 点，前端画 400 点其实够，但 JSON 传输开销大（每点 2 个数字）。

做法：**服务端降采样到 180 点**（2° 一格，取最小值），用短键压缩：

```json
{ "t":"scan", "ts":..., "n":180, "r":[1234,1250,-1,1180,...] }
```
`-1` 表示无效点。180 个整数 ≈ 1KB，5Hz 仅 40kbps。

> 完整 400 点、0.9° 精度的点云**只在 rviz2 里看**，Web 端不需要。

## 6. 安卓端：PWA 优先，不做原生

### 6.1 三种方案对比

| 方案 | 开发成本 | 体验 | 能力 | 推荐 |
|---|---|---|---|---|
| **PWA（同一套 Web 代码）** | **0**（复用） | 接近原生 | 无后台/无蓝牙 | ✅ **首选** |
| Capacitor 包壳 | 低（半天） | 同 PWA | 加原生插件（后台、通知） | ✅ 需要装 APK 时用 |
| 原生 Kotlin | **高（×3）** | 最好 | 全能力 | ❌ 不值得 |

**结论**：一套 Vue 代码同时服务 Windows 浏览器和安卓。先用 PWA（浏览器"添加到主屏幕"），需要独立 APK 时再用 Capacitor 包一层，**代码零改动**。

### 6.2 PWA 在安卓上的限制（提前知道）

| 限制 | 影响 | 对策 |
|---|---|---|
| 后台会被杀 | 切到别的 App 再回来要重连 | 重连时重新拉 `/api/status` |
| 无屏幕常亮 API（部分支持） | 长时间遥控会黑屏 | 用 `navigator.wakeLock`（Chrome 支持） |
| 触摸延迟 | 比原生高 10~20ms | 可接受 |
| 无物理按键映射 | 不能用手柄键 | 需要时上 Capacitor |
| HTTP 下不能用 WakeLock/ServiceWorker | 必须 HTTPS 或 localhost | 局域网用 `http://IP` 时功能受限 → 部署 Caddy 上 HTTPS |

> 🔴 **最后一条很关键**：PWA 的 Service Worker 和 WakeLock 只在**安全上下文**（HTTPS 或 localhost）可用。局域网 `http://192.168.x.x` 是**不安全上下文**，PWA 装不上、屏幕会黑。
> 对策：局域网也上 **Caddy 自签/内网证书**，或者用 `mkcert` 生成内网证书。

## 7. 视频链路

### 7.1 数据来源

```
OV2640 ──DVP──► 板2 ──JPEG 40KB/帧──UDP 8891──► cam_bridge ──► /image_raw/compressed
```

`cam_bridge` 不解码、不转码，**原样转发**（省 CPU）。

### 7.2 三阶段演进

| 阶段 | 方案 | 延迟 | 复杂度 | 何时用 |
|---|---|---|---|---|
| **V1** | gateway → WS 二进制 → Canvas | 80~200ms | 低 | 起步就用这个 |
| **V2** | mediamtx + WebRTC（WHIP） | 50~120ms | 中 | 遥控手感不够时 |
| V3 | WebRTC + TURN（公网） | 80~250ms | 高 | 公网遥控必配 |

**V1 实现（推荐先做）**

```
后端：
  @app.websocket("/ws/video")
  async def video_ws(ws):
      await ws.accept()
      while True:
          jpg = await latest_jpeg()          # 从 ROS 订阅拿最新帧
          await ws.send_bytes(header + jpg)  # header: seq(u32) + ts_ms(u64)

前端：
  const bmp = await createImageBitmap(new Blob([data.slice(12)]));
  ctx.drawImage(bmp, 0, 0, W, H);
```

**为什么不分片**：一帧 40KB，WS 单帧上限足够（默认 1MB+）。分片是 UDP 时代的需求，TCP/WS 不需要。

### 7.3 自适应码率（远程必做）

| 场景 | 分辨率 | 帧率 | 质量 | 码率 |
|---|---|---|---|---|
| 局域网 | SVGA 800×600 | 10 | 12 | 3.2 Mbps |
| 公网（4G/弱网） | VGA 640×480 | 8 | 18 | 1.0 Mbps |
| 公网（很差） | QVGA 320×240 | 5 | 25 | 0.3 Mbps |

**触发逻辑**：前端统计"最近 10 帧的平均到达间隔 + 帧大小"，超过阈值就 `POST /api/camera` 降档；恢复后自动升档。

> ESP32 侧已有 `0x54` 帧支持动态调分辨率/帧率/质量，**不需要改固件**。

## 8. 公网远程

### 8.1 四种方案对比

| 方案 | 需要什么 | 延迟 | 安全 | 代码改动 | 适合 |
|---|---|---|---|---|---|
| **Tailscale** | 两端装客户端 | 低（P2P 直连） | 高（WireGuard） | **0** | ✅ **起步首选** |
| Cloudflare Tunnel | 域名 + 客户端 | 中（走 CF 边缘） | 高（TLS） | 0 | 分享给他人 |
| frp | 有公网 VPS | 中 | 中（自己管） | 0 | 有 VPS 且要控 |
| 自建中转 | VPS + 写服务 | 中 | 可控 | **大** | 产品化才需要 |
| WebRTC + TURN | VPS（TURN） | 低 | 中 | 中 | 视频低延迟刚需 |

### 8.2 推荐路径（三级递进）

```
阶段 1｜局域网
  手机/PC 与车在同一 WiFi → http(s)://<上位机IP>:8080
  特点：零配置，延迟最低（20ms）

★ 阶段 2｜Tailscale（本项目定案）★
  WSL2/Windows 装 Tailscale → 手机装 → 同一 tailnet
  访问 http://<tailscale-IP>:8080
  特点：零代码改动，WireGuard 加密，无需公网 IP，无需端口映射，点对点直连
  限制：只有自己（和受邀设备）能访问 —— 本项目正是自己用，完全匹配

阶段 3｜Cloudflare Tunnel（**本项目不做**，仅记录备选）
  仅当未来需要"发个链接给别人看"时才考虑
```

> ✅ **定案：只做 Tailscale，不做 Cloudflare Tunnel、不自建中转、不买 VPS。**
> 理由：自用场景下 Tailscale 覆盖全部需求，且加密、免公网 IP、零代码。多一层公网暴露就多一份风险，没必要。

### 8.3 WSL2 + Tailscale 的坑（**重要**）

Win11 的 `mirrored` 网络模式下，WSL2 直接共享宿主网络接口，**通常**能通过宿主的 Tailscale IP 访问 WSL2 里的服务。但 VPN/虚拟网卡在 mirrored 模式下**历史上有兼容问题**。

**验证步骤**：

```powershell
# 1. 确认 WSL 配置
# C:\Users\<你>\.wslconfig
[wsl2]
networkingMode=mirrored

```


| 退路 | 做法 |
|---|---|

## 9. 安全设计

### 9.1 必做清单

| # | 措施 | 说明 |
|---|---|---|
| 1 | **JWT 鉴权** | 除了 `/api/auth/login`，所有接口都要 token |
| 2 | **HTTPS/WSS** | Caddy 自动证书；内网用 mkcert |
| 3 | **死手开关** | 见 §4.5，500ms 无指令即停 |
| 4 | **服务端限幅** | 不信前端，`vx/vw` 二次 clamp |
| 5 | **急停不受鉴权阻塞** | estop 接口即使 token 过期也放行（或单独长期 token） |
| 6 | **不暴露 ROS2 DDS** | 只暴露 8080，绝不把 DDS 端口映射出去 |
| 7 | **登录失败限流** | 5 次/分钟，防暴力破解 |
| 8 | **视频不落盘** | 默认不录像，需要时手动开 |
| 9 | **操作留痕** | 每条控制指令记 (who, when, what) |

### 9.2 权限分级

| 角色 | 权限 |
|---|---|
| `viewer` | 看视频、看状态、看地图 |
| `operator` | + 控制移动、云台、导航 |
| `admin` | + 改配置、OTA、重启 |

> 自用场景下不需要复杂的多用户，一个 `admin` 就够。分级留着，为了以后能加"只读观众"。

### 9.3 🔴 急停只有网页按钮：风险与五层补偿

**本项目决定：不做物理急停按钮，急停是 Web 界面上的一个红色按钮。**

这个决定本身没问题（省一个 GPIO，板 1 的 IO 本来就满），但必须清楚它的**失效边界**：

| 场景 | 网页急停还能用吗 |
|---|---|
| 正常遥控中 | ✅ 能（点一下 200ms 内停） |
| WiFi 断了 | ❌ **点不到** |
| 上位机崩了 | ❌ **点不到** |
| 手机/浏览器崩了 | ❌ **点不到** |
| 网页卡住 | ⚠️ 可能要等几秒 |

**网页急停只能处理"操作失误"，处理不了"链路故障"。** 链路故障必须由另外几层兜住：

```
第 1 层｜网页急停按钮（+ 空格键）  ← 处理操作失误
   ↓ 链路断了这层失效
第 2 层｜死手开关（服务端）        ← 500ms 收不到 cmd 就归零
   ↓ 上位机崩了这层也失效
第 3 层｜板 1 本地超时            ← ★ 固件里，不依赖上位机
   ↓ 只有板 1 自己崩才失效
第 4 层｜硬件看门狗               ← 10s 复位
   ↓
第 5 层｜电池总开关（物理拔电）    ← 不占 GPIO，必须有
```

**五层缺一不可。** 第 3 层是**唯一不依赖 WiFi 的软件层**，实现要点：

```c
/* 板 1：通信超时监控，由 sys 任务每 10ms 检查 */
static uint32_t s_last_cmd_ms = 0;

void sys_check_link_timeout(void)
{
    uint32_t now = millis();
    if (now - s_last_cmd_ms > 500) {
        if (!g_link_lost) {
            g_link_lost = true;
            mtr_emergency_stop();              /* 见下方实现 */
            g_sys.fault_code |= FAULT_LINK_LOST;
            ui_show_offline(true);
        }
    }
}
```

**`mtr_emergency_stop()` 的实现顺序（v1.0 明确）**

```c
void mtr_emergency_stop(void)
{
    for (uint8_t ch = 0; ch < 2; ch++) {
        /* ① 短路刹车：AIN1=AIN2=H，PWM=0 */
        drv_tb6612_set_dir(ch, TB_DIR_BRAKE);
        drv_tb6612_set_pwm(ch, 0);
    }
    /* ② 再切断 STBY（防止 PWM 脚悬空抖动） */
    drv_tb6612_set_standby(false);

    g_mtr.estop = true;
}
```

> ⚠️ **两个必须写死的语义**（否则实现者很容易搞错）：
>
> 1. **STBY 拉低 = 高阻滑行（coast），不是刹车。** 单靠 `STBY=L` 停车，车会以 0.6 m/s 继续滑行约 37 cm、耗时约 1.2 秒——这段时间完全不受控。所以**刹车必须先于 STBY 切断**，且靠的是 `AIN1=AIN2=H` 的绕组短接。
> 2. **顺序不可颠倒。** 先 `STBY=L` 时 H 桥已断开，此时设 AIN 无效，电机只会滑行。恢复时相反：先 `STBY=H` 让 H 桥就绪，再设方向与 PWM。
>
> 详见 `04` §4.1。

**另外五条约束**

| # | 约束 | 理由 |
|---|---|---|
| 1 | 急停按钮**常驻可见**，不被弹窗/翻页遮住 | 慌乱时找按钮 = 撞墙 |
| 2 | 急停同时发 **REST + WebSocket 两条**，哪条先到算哪条 | 单链路可能阻塞 |
| 3 | 急停接口**不受 token 过期影响** | 安全优先于鉴权 |
| 4 | 键盘 `空格` 也绑定急停 | PC 端多一条路 |
| 5 | **电池总开关必须一只手够得到** | 最后的物理手段 |

> 本项目不做断电刹车（TT 马达无制动器），但**拔电池**永远有效。

### 9.4 三条红线

1. **绝不在没有第 2 层（死手）+ 第 3 层（板端超时）的情况下做遥控。**
2. **绝不把 8080 直接映射到公网**（用 Tailscale，自带 WireGuard 加密）。
3. **绝不让 ESP32 直接暴露在公网**（它们只在局域网，由上位机代理）。

## 10. 预算

### 10.1 延迟预算（遥控手感）

| 环节 | 局域网 | 公网（4G） |
|---|---|---|
| ESP32 → 上位机 | 15 ms | 15 ms |
| 上位机处理 | 5 ms | 5 ms |
| 上位机 → 客户端 | 20 ms | 80~150 ms |
| 视频解码 + 显示 | 30 ms | 30 ms |
| **合计** | **~70 ms** | **~200 ms** |

> 0.3 m/s 下，200ms 对应 6cm 位移。可接受。**超过 400ms 就必须降速**。

### 10.2 带宽预算

| 流 | 码率 | 说明 |
|---|---|---|
| 视频（局域网） | 3.2 Mbps | SVGA@10fps |
| 视频（公网） | 0.3~1.0 Mbps | 自适应降档 |
| 遥测 WS | 0.1 Mbps | 10Hz JSON |
| 点云 WS | 0.04 Mbps | 5Hz×180 点 |
| 控制 WS | 0.01 Mbps | 20Hz |
| **合计（局域网）** | **~3.4 Mbps** | 家宽上行通常 10~30Mbps，够 |
| **合计（公网）** | **~0.5 Mbps** | 4G 也够 |

### 10.3 上位机算力评估（**按实测硬件**）

**实测配置**

| 项 | 参数 | 评注 |
|---|---|---|
| CPU | **i5-6300HQ**（2015，Skylake） | **4 核 4 线程**，无超线程，2.3~3.2GHz |
| 内存 | **20 GB** | 充裕，不是瓶颈 |
| 显卡 | **GTX 950M 4GB**（Maxwell，CC 5.0） | 约 1.2 TFLOPS，**无 Tensor Core** |
| 系统 | Windows 11 + WSL2 Ubuntu 22.04 | 需 `networkingMode=mirrored` |

**逐项占用估算**

| 任务 | CPU 占用 | 说明 |
|---|---|---|
| ROS2 核心 + 5 个桥接节点 | 0.4 核（10%） | Python 节点，轻 |
| `slam_toolbox` | 0.5~0.8 核（15~20%） | 400 点/圈、10Hz，负载不高 |
| Nav2 | 空闲 0.2 核 / 规划时 0.6 核 | 只在导航时吃 |
| `sherpa-onnx` 流式中文 | 1~1.5 核（25~35%） | **2 线程**，只在说话时 |
| `web_gateway`（FastAPI） | 0.2 核（5%） | — |
| `vision_yolo`（GPU） | 0.3 核 + **GPU 60~80%** | 10fps 输入 |
| **合计（稳态）** | **~3.1 / 4 核（78%）** | 可行，但**没有余量** |

**四条硬结论**

1. **YOLO 必须上 GPU，且必须间歇运行。**
   GTX 950M 跑 YOLOv8n@640 大约 **10~15 FPS**（Maxwell 无 Tensor Core，TensorRT 最多到 20+）。
   够用，但**不能常开**。策略：默认 3fps 检测，识别到目标才升到 10fps。

2. **rviz2 不要常开。**
   它是 1 核 + 大量 GPU，开着就把余量吃光。
   → 可视化改用 **Windows 侧 Foxglove Studio**（走 WebSocket 连 `foxglove_bridge`），或只在需要时开 rviz。

3. **4 核 4 线程是硬限制。**
   进程一多就排队。建议把 `device_io` / `lidar_bridge` / `cam_bridge` / `audio_bridge` 合到一个进程（单 rclpy 节点 + 多线程执行器），省下 4 个 Python 解释器的开销。

4. **ASR 与 SLAM 不要同时高负载。**
   说话时 ASR 吃 1.5 核，如果正在建图会卡。策略：建图时降低 ASR 线程数，或只在停车时接受语音。

### 10.4 ✅ GTX 950M 验证（**已于 2026-11-08 实测完成，本节保留作记录**）

> **结论先说：950M 在 WSL2 里完全可用，走主方案，不需要方案 B。**
>
> 实测数据见 `16` §6。摘要：

| 验证项 | 结果 | 实测值 |
|---|---|---|
| WSL2 能否看到显卡 | ✅ 可以 | `nvidia-smi` 显示 GTX 950M，4096 MiB |
| `/dev/dxg` 设备节点 | ✅ 存在 | 驱动 582.78（WSL 内 580.178.01） |
| PyTorch CUDA 可用 | ✅ True | torch 2.1.2+cu118，sm_50 |
| 实际算力 | ✅ 可用 | 1024² matmul 4.47 ms |
| YOLOv8 前向 | ✅ PASS | ultralytics 8.4.204 |

**结论对本文档的影响：**

1. `vision_yolo` 直接跑在 WSL2 里，**不需要方案 B 的跨系统桥接**
2. §10.3 的 CPU 预算表按"GPU 可用"那一列执行（YOLO 仅占 0.3 核，GPU 60~80%）
3. **不要再重复验证这两项**——已做过了，重复只是浪费时间

**仍然成立的约束**：`torch` 必须锁 `2.1.2+cu118`。Maxwell 架构在 PyTorch 2.6+ 已被移除，升级即失效。详见 `16` §9.2。

**方案 B（仅作历史记录，当前不启用）**

```
Windows 原生 Python + YOLOv8（直接用 950M，无需 WSL2 虚拟化）
        │
        │ TCP/UDP 发送检测结果（JSON：框 + 类别 + 置信度）
        ▼
WSL2 里的 ROS2 节点 → /detections
```

若将来换到一台 WSL2 看不到显卡的机器，这条退路仍然有效——因为视觉本来就是独立模块，在哪里跑不影响其他部分。

## 12. 全链路接口映射

**这是 SDD 最需要的一张表**：同一个"速度"，在四个地方有四种形态。

| 语义 | ESP32 侧 | L1 帧 | ROS2 话题 | L2 消息 |
|---|---|---|---|---|
| 速度指令 | `mtr_set_velocity()` | `0x50`（7 B，含 L1 seq） | `/cmd_vel` Twist | `{"t":"cmd","vx":0.3,"seq":1234}` |
| 里程计 + **位姿** | `odom_get()` | `0x10`（17 B，含位姿） | `/odom` | `{"odom":{"x":..,"y":..,"th":..}}` |
| 姿态 | `imu_read_attitude()` | `0x11` | `/imu` | `{"imu":{..}}` |
| 电池 | `pwr_get()` | `0x12` | `/battery` | `{"batt":{..}}` |
| 系统状态 | `sys_get_status()` | `0x13`（16 B，含 uptime/版本） | `/robot_status` | `{"sys":{..}}` |
| 激光点云 | `lidar_fetch_scan()` | `0x20` | `/scan` | `{"t":"scan","r":[..]}` |
| 摄像头 | `cam_capture()` | `0x21` | `/image_raw/compressed` | WS 二进制 |
| 语音录音 | `aud_read_pcm()` | `0x23` | `/audio/in` | （不对外） |
| 语音意图 | — | `0x14` | `/voice/intent` | `{"t":"intent"}` |
| 云台 | `srv_set_angle()` | `0x51` | `/pan_tilt/cmd` | `{"t":"servo"}` |

> 换任何一个环节，只要对得上这张表的某一行，系统就能跑通。**这就是接口契约的价值**。
>
> **注意"里程计"这一行**：位姿（x/y/θ）由板 1 积分后随 `0x10` 上行，gateway **只做类型转换**写进 `/odom`，**不做任何积分**。v0.1 曾让上位机用轮速重新积分，会导致 `/odom` 与 `tf` 撕裂（见 `02` §9.1）。

## 15. 一句话总结

**L1 是"设备语言"（二进制/UDP，只给固件和桥接用），L2 是"人的语言"（JSON/WS，给浏览器和手机用）。中间那层 gateway 既是翻译官，也是安全闸门——死手开关、鉴权、限幅全在它这里。**

前端一套 Vue 代码同时服务 Windows 和安卓（PWA），公网先用 Tailscale 零成本打通，需要分享再上 Cloudflare Tunnel。
