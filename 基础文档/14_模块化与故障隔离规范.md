# 14 · 模块化与故障隔离规范

> 项目：ESP32-S3 两轮差速 ROS2 智能小车
> 文档版本：**v1.0**　｜　正式发布版
> 生成日期：2026-11-07
> 性质：**开发宪法**——所有模块的设计、编码、测试都必须遵守本文档

---

## 0. 为什么需要这份文档

一句话目标：

> **任何一个模块写坏了，整车不能因此瘫痪；任何一个模块改动了，不需要重新验证全部。**

这不是靠"写代码时小心一点"能实现的，必须靠**结构性约束**。本文档定义五层隔离：

| 层 | 隔离什么 | 手段 |
|---|---|---|
| 编译期 | 模块之间的依赖 | 目录 + 头文件白名单 + 单向依赖 |
| 运行期 | 崩溃/卡死扩散 | 独立任务 + 队列通信 + 分层看门狗 |
| 功能级 | 单点故障导致全车不可用 | 降级矩阵 |
| 开发期 | 改 A 影响 B | 纯算法与硬件分离 + PC 端单元测试 |
| 发布期 | 一块板升级失败拖累其他 | 独立固件 + 独立 OTA + 版本校验 |

---

## 1. 五条铁律

写在最前面，任何时候不得违反：

| # | 铁律 | 违反后果 |
|---|---|---|
| **L1** | **一个模块只做一件事，只暴露一个头文件** | 边界模糊，改动扩散 |
| **L2** | **依赖只能单向：驱动 → 功能 → 应用**，禁止环依赖 | 编译耦合，无法单独测试 |
| **L3** | **跨模块通信只能走队列或事件组**，禁止直接读写别人的全局变量 | 竞态、隐性耦合 |
| **L4** | **纯算法（PID/运动学/协议/解析）不得包含任何硬件头文件** | 无法在 PC 上测试，只能上板试错 |
| **L5** | **每个模块必须能"单独编译、单独烧录、单独验证"** | 只能整车联调，一次改动验证成本极高 |

## 2. 编译期隔离

### 2.1 目录结构（PlatformIO 单仓三环境）

```
robot_fw/
├── platformio.ini
├── lib/                          # 三块板共用
│   ├── proto/                    # ★ 纯 C：X-Protocol 编解码
│   │   ├── library.json
│   │   ├── include/proto.h
│   │   └── src/proto.c
│   ├── kin/                      # ★ 纯 C：运动学 + 里程计
│   ├── pid/                      # ★ 纯 C：增量式 PID
│   ├── lidar_parse/              # ★ 纯 C：D6 点云解析
│   ├── img_chunk/                # ★ 纯 C：JPEG 分片重组
│   ├── bsp_common/               # 板级基础（WiFi/OTA/日志）
│   ├── drv_tb6612/               # 硬件驱动
│   ├── mod_mtr/                  # 功能模块：电机闭环
│   ├── mod_imu/
│   ├── mod_pwr/
│   ├── mod_srv/
│   ├── mod_ui/
│   ├── mod_lid/
│   ├── mod_cam/
│   ├── mod_aud/
│   └── mod_net/                  # UDP 收发
├── src/
│   ├── main_board1.cpp           # 主控
│   ├── main_board2.cpp           # 感知
│   └── main_board3.cpp           # 音频
├── test/                         # ★ PC 端单元测试
│   ├── test_proto/
│   ├── test_kin/
│   └── test_lidar_parse/
└── examples/                     # 每模块独立可烧录示例
    ├── ex_mtr/
    ├── ex_ui/
    └── ...
```

> ★ 标记的是**纯算法模块**：不含 `Arduino.h`、不含 `driver/*.h`、不含 `WiFi.h`。
> 这些模块能在 PC 上编译运行，**不需要插硬件**。

### 2.2 依赖方向（单向，不可逆）

```
应用层    main_boardN.cpp / sys 状态机
             │
功能层    mod_mtr  mod_imu  mod_ui  mod_lid  mod_cam  mod_aud  mod_net
             │
驱动层    drv_tb6612  drv_lcd  drv_i2c  drv_uart
             │
基础层    bsp_common（WiFi / OTA / 日志 / NVS）
             │
算法层    proto  kin  pid  lidar_parse  img_chunk   ← 谁都可以用，它不依赖任何人
```

**规则**

| 规则 | 说明 |
|---|---|
| 上层可以调下层 | `mod_mtr` 可以调 `pid` 和 `drv_tb6612` |
| **下层不能调上层** | `pid` 绝不能 `#include "mod_mtr.h"` |
| **同层不横向调** | `mod_ui` 不许直接调 `mod_mtr`，要走 `sys` 或队列 |
| **算法层零依赖** | `proto`/`kin`/`pid` 只依赖 `<stdint.h>` `<string.h>` `<math.h>` |

> 同层横向调用是**最常见也最致命的耦合**。UI 想显示速度？不要 `mtr_get_speed()` 直接读，让 `sys` 把数据放进 `g_ui_data` 里，UI 只读 `g_ui_data`。

### 2.3 头文件规范

每个模块只暴露一个 `include/xxx.h`，里面只有：

```c
#ifndef MOD_MTR_H
#define MOD_MTR_H

#include <stdint.h>
#include <stdbool.h>

/* ===== 类型 ===== */
typedef struct { ... } mtr_wheel_t;

/* ===== 常量（只有调用方需要的才放这里） ===== */
#define MTR_VX_LIMIT 0.6f

/* ===== 接口 ===== */
bool mtr_init(void);
bool mtr_set_velocity(float vx, float vw);
void mtr_get_snapshot(mtr_wheel_t *out);

#endif
```

**禁止出现在公共头文件里**

| 禁止项 | 原因 |
|---|---|
| `#include "Arduino.h"` | 把硬件依赖传染给所有调用方 |
| 内部 static 变量声明 | 暴露实现 |
| 具体引脚号 | 引脚只在 `board_pinmap.h` |
| 别人的头文件 | 依赖扩散 |
| `using namespace` | 污染 |

### 2.4 自动检查（写个脚本，提交前跑）

```python
# tools/check_deps.py —— 检查依赖违规
RULES = {
    "lib/proto":     [],                                   # 算法层不许依赖任何项目模块
    "lib/kin":       [],
    "lib/pid":       [],
    "lib/lidar_parse": [],
    "lib/bsp_common": ["freertos", "esp_", "WiFi"],
    "lib/drv_*":     ["bsp_common"],
    "lib/mod_*":     ["drv_*", "proto", "kin", "pid", "bsp_common"],
}
# 1. 扫描每个 lib 的 #include
# 2. 算法层出现 Arduino.h / driver/ / WiFi.h → 报错
# 3. 出现反向依赖（下层 include 上层）→ 报错
# 4. 出现环依赖 → 报错
```

> 这个脚本 100 行以内，**但它是"模块化"能不能守住的关键**。人在赶进度时一定会图省事跨层调用，只有自动化检查能拦住。

## 3. 运行期隔离

### 3.1 任务划分原则

| 模块类型 | 是否独立任务 | 理由 |
|---|---|---|
| 有阻塞 I/O（UART/I2C/SPI 等待） | **必须独立任务** | 阻塞会拖垮调用者 |
| 周期采样（10~100Hz） | **必须独立任务** | 需要稳定周期 |
| 纯计算（PID 一步、解析一包） | **不开任务**，由调用者驱动 | 开任务反而增加开销和竞态 |
| 事件响应（按键、命令） | 队列 + 一个消费者任务 | — |

**反例**：给 `pid` 开一个任务，通过队列喂数据——纯属浪费，还引入延迟。

### 3.2 模块生命周期（统一 API）

每个模块必须有这四个函数，签名固定：

```c
bool xxx_init(void);        /* 只做一次：申请资源、配置硬件。失败返回 false */
bool xxx_start(void);       /* 创建任务、开始工作 */
bool xxx_stop(void);        /* 停任务、关输出、保持资源 */
bool xxx_is_healthy(void);  /* 健康检查：最近一次心跳是否超时 */
```

**约定的行为**

| 场景 | 要求 |
|---|---|
| `init()` 失败 | 记录故障码，**不阻塞其他模块初始化** |
| 模块内部异常 | 自己 `stop()`，置 unhealthy，通过 `sys` 上报 |
| `stop()` | 必须把输出置于**安全状态**（电机 PWM=0、舵机保持、功放静音） |
| `is_healthy()` | 供 `sys` 巡检，不自己做恢复动作 |

### 3.3 跨模块通信：只允许两种方式

**方式 A：数据流 → 队列（拷贝值，不传指针）**

```c
/* 生产者：mtr 每 10ms 投递一次 */
mtr_sample_t s = { .rt_mps = ..., .pwm = ... };
xQueueOverwrite(g_q_mtr, &s);      /* 只保留最新值，用 Overwrite */

/* 消费者：net 组包时取 */
mtr_sample_t s;
if (xQueuePeek(g_q_mtr, &s, 0) == pdTRUE) { ... }
```

> 用 `xQueueOverwrite` + 深度 1，天然实现"只要最新值"。比加锁简单，也不会阻塞。

**方式 B：状态位 → 事件组**

```c
#define EVT_WIFI_OK      (1 << 0)
#define EVT_LIDAR_OK     (1 << 1)
#define EVT_EMERGENCY    (1 << 2)

xEventGroupSetBits(g_sys_evt, EVT_LIDAR_OK);
```

**禁止**：直接读别人的 `g_xxx` 可变全局。只读快照要走 `xxx_get_snapshot()`（内部加锁拷贝）。

### 3.4 分层看门狗

| 层 | 超时 | 动作 |
|---|---|---|
| **硬件 WDT**（`esp_task_wdt`） | 10 s | 整机复位（最后手段） |
| **任务心跳** | 各模块自定 | 心跳停 → 该模块 `stop()` + 置故障 |
| **通信超时** | 500 ms | 电机停（这条保命） |
| **模块自检** | 1 s | 连续 N 次失败 → 降级 |

**关键**：只有 `sys` 任务喂硬件看门狗。其他模块通过队列上报心跳。这样任何一个模块卡死，`sys` 能感知；`sys` 自己卡死，硬件复位。

## 4. 故障降级矩阵（核心）

> 这张表回答一个问题：**某个模块挂了，整车还能干什么？**

### 4.1 板 1 · 主控

| 故障模块 | 现象 | 降级策略 | 整车可用性 |
|---|---|---|---|
| **`mtr` 完全失效** | 轮子不转 | 停车，屏幕/Web 报警 | ❌ 不可移动 |
| **单轮编码器失效** | 速度反馈缺失 | 该轮切开环，**限速 30%**，禁用建图，仅手动遥控 | ⚠️ 受限可动 |
| **`imu` 失效** | 无姿态 | 里程计仍靠编码器；SLAM 仍可用雷达；云台增稳失效 | ✅ 基本可用 |
| **`pwr` 失效** | 无电压电流 | 按运行时长方估电量，限速，提示"电量未知" | ✅ 可用 |
| **`srv` 失效** | 云台不动 | 摄像头固定视角，视觉可用（视角变窄） | ✅ 可用 |
| **`ui` 失效** | 屏幕黑 | **Web 端全功能接管**，屏幕非必需 | ✅ 可用 |
| **`net` 失效（WiFi 断）** | 失联 | **500ms 超时自动停车**，进入本地待机 | ⚠️ 停但安全 |
| **`sys` 失效** | 状态机异常 | 硬件看门狗复位 | ⚠️ 重启恢复 |

### 4.2 板 2 · 感知

| 故障模块 | 现象 | 降级策略 | 对整车影响 |
|---|---|---|---|
| **`cam` 失效** | 无图传 | 关闭视觉功能，仅靠雷达，**限速 50%** | ⚠️ 盲开（有雷达） |
| **`lid` 失效** | 无点云 | 无法建图/导航；已有地图也不能用（无定位） | ⚠️ 只能手动遥控 |
| 板 2 整板离线 | 两者皆无 | 同 lid 失效 | ⚠️ 手动遥控 |

### 4.3 板 3 · 音频

| 故障模块 | 降级策略 | 影响 |
|---|---|---|
| **`aud` 失效** | 无语音输入输出 | ✅ 无影响（语音是增强功能） |
| 板 3 整板离线 | 忽略 | ✅ 无影响 |

### 4.4 上位机

| 故障 | 降级策略 | 影响 |
|---|---|---|
| `device_io` 挂 | 板 1 超时停车 | ⚠️ 停 |
| `web_gateway` 挂 | **不影响 ROS2**，可用 rviz/命令行接管；重启 gateway 即可 | ✅ 可恢复 |
| `slam_toolbox` 挂 | 切手动遥控 | ⚠️ 无地图 |
| `nav2` 挂 | 切手动遥控 | ⚠️ 无导航 |
| `voice_asr` 挂 | 语音失效，其他正常 | ✅ 可用 |
| 上位机整机崩 | 板 1 超时停车 | ⚠️ 停 |

### 4.5 由矩阵反推的三条设计约束

1. **语音、屏幕、云台必须是"可选增强"**——任何一个挂了，车都能正常开。这是它们优先级定为 P2 的原因。
2. **`net` 失效必须能本地停车**——所以超时逻辑在**板 1 上**，不能依赖上位机。
3. **板 2 挂掉等于失去导航能力**——所以手动遥控链路必须独立于板 2（走板 1），这也是星型拓扑的价值。

## 5. 故障注入（验证降级矩阵的唯一方法）

写完了降级矩阵，**不等于它能工作**。必须能主动把模块弄坏，看系统是否按预期降级。

### 5.1 注入接口

每个模块提供（仅调试固件编译）：

```c
#ifdef CONFIG_FAULT_INJECT
typedef enum {
    FI_NONE = 0,
    FI_INIT_FAIL,        /* init 返回 false */
    FI_RX_TIMEOUT,       /* 模拟收不到数据 */
    FI_DATA_CORRUPT,     /* 数据全 0 / 全 0xFF */
    FI_TASK_HANG,        /* 任务卡死（vTaskDelay 100s） */
    FI_SENSOR_DEAD,      /* 传感器无响应 */
} fi_mode_t;

void xxx_debug_fault(fi_mode_t mode);
#endif
```

### 5.2 验证清单（每个模块上线前必跑）

| # | 注入 | 期望 |
|---|---|---|
| 1 | `mtr` FI_TASK_HANG | 硬件 WDT 10s 内复位，复位后能正常启动 |
| 2 | `net` FI_RX_TIMEOUT | 500ms 内电机停，屏幕显示"离线" |
| 3 | `lid` FI_SENSOR_DEAD | 上报故障码，SLAM 停止，手动遥控仍可用 |
| 4 | `cam` FI_DATA_CORRUPT | 上位机丢弃花屏帧，不崩溃 |
| 5 | `imu` FI_INIT_FAIL | 其他模块正常启动，里程计仍工作 |
| 6 | `ui` FI_INIT_FAIL | 屏幕不亮，Web 端功能完整 |
| 7 | `aud` FI_TASK_HANG | 语音无响应，其他正常 |

> **这 7 条跑通，"一块坏了不影响其他"才算真的成立**，而不只是写在文档里。

## 6. 测试金字塔（开发期隔离）

```
        ┌─────────────┐
        │  整车联调    │  少、慢、贵
        ├─────────────┤
        │  硬件在环    │  单板上真实外设
        ├─────────────┤
        │  回环测试    │  ESP32 自发自收
        ├─────────────┤
        │  PC 单元测试 │  ★ 多、快、免费
        └─────────────┘
```

### 6.1 PC 单元测试（最重要的一层）

PlatformIO 支持 `platform = native`，纯算法模块可以在**电脑上直接跑测试**，不用插板子。

```ini
; platformio.ini
[env:native]
platform = native
test_framework = unity
build_flags = -DUNIT_TEST -std=gnu++17
lib_deps =
    throwtheswitch/Unity@^2.5.2
```

```bash
pio test -e native          # 跑所有单测，秒级完成
```

**哪些能测**

| 模块 | 测什么 | 价值 |
|---|---|---|
| `proto` | 组帧/解帧/校验和/边界长度/坏帧 | ★★★★★ 协议错一个字节整条链路废 |
| `kin` | 正逆解、轮距变化、里程计积分 | ★★★★★ 算错了车走不直 |
| `pid` | 阶跃响应、限幅、抗饱和 | ★★★★ 不用反复烧板试参数 |
| `lidar_parse` | 用真实抓包数据回放，比对解析结果 | ★★★★★ 协议复杂，必须逐字节验 |
| `img_chunk` | 乱序/丢片/重复片的重组 | ★★★★ 图传花屏的根因多在这 |

**示例：协议测试**

```c
void test_proto_velocity_frame(void)
{
    uint8_t buf[16];
    int n = proto_pack_velocity(buf, 0.3f, 0.0f, 0.5f);
    TEST_ASSERT_EQUAL_INT(11, n);
    TEST_ASSERT_EQUAL_HEX8(0xAA, buf[0]);
    TEST_ASSERT_EQUAL_HEX8(0x55, buf[1]);
    TEST_ASSERT_EQUAL_HEX8(0x0B, buf[2]);
    TEST_ASSERT_EQUAL_HEX8(0x50, buf[3]);
    TEST_ASSERT_EQUAL_HEX8(0x01, buf[4]);   /* VX hi */
    TEST_ASSERT_EQUAL_HEX8(0x2C, buf[5]);   /* VX lo */
    TEST_ASSERT_EQUAL_HEX8(0x7C, buf[10]);  /* checksum */
}
```

> 这条测试跑一次 1 毫秒，覆盖了烧板测试 10 分钟才能发现的问题。

### 6.2 回环测试

ESP32 自己发、自己收，验证 `net` 层收发闭环：

```
mod_net 发 0x13 → UDP 回环 → mod_net 收 → 比对字段
```

不需要上位机、不需要另一块板。

### 6.3 硬件在环（单模块）

每个模块一个 `examples/ex_xxx/`，可以**单独烧录**，不依赖其他模块：

```c
// examples/ex_mtr/main.cpp —— 只测电机，不联网不连屏
void setup() {
    Serial.begin(115200);
    mtr_init();
    mtr_set_velocity(0.3f, 0.0f);       // 前进 0.3 m/s
}
void loop() {
    mtr_wheel_t w[2];
    mtr_get_snapshot(w);
    Serial.printf("L=%.3f R=%.3f\n", w[0].rt_mps, w[1].rt_mps);
    delay(100);
}
```

**这是"一个功能一个功能写"的物理载体**——写完一个模块，先让它在 example 里独立跑通，再接进主固件。

## 7. 开发节奏：一次只做一个块

### 7.1 单块的完整闭环（DoD）

一个模块从开始到"完成"，必须走完六步，**缺一步不算完成**：

| 步 | 产出 | 验收 |
|---|---|---|
| 1. Spec | 1 页内的模块规格（输入/输出/时序/故障） | 评审通过 |
| 2. 接口 | `include/xxx.h`，签名冻结 | 编译通过 |
| 3. 单测 | `test/test_xxx/`（纯算法必须有） | `pio test -e native` 全绿 |
| 4. Example | `examples/ex_xxx/` 可独立烧录 | 硬件行为符合 spec |
| 5. 故障注入 | 按 §5.2 跑对应项 | 降级符合矩阵 |
| 6. 集成 | 接入 `main_boardN.cpp` | 不破坏已通过的其他模块 |

### 7.2 集成顺序（依赖拓扑序）

```
第 1 批（无依赖）:
  proto → kin → pid → lidar_parse → img_chunk
  ↑ 全部可 PC 单测，不碰硬件

第 2 批（基础层）:
  bsp_common（WiFi/OTA/NVS/日志）

第 3 批（驱动层，可并行）:
  drv_tb6612 │ drv_lcd │ drv_i2c │ drv_uart

第 4 批（功能模块，可并行）:
  mod_mtr │ mod_imu │ mod_pwr │ mod_srv │ mod_ui │ mod_lid │ mod_cam │ mod_aud │ mod_net

第 5 批（应用）:
  sys 状态机 + main_boardN

第 6 批（上位机）:
  device_io → gateway → web 前端
```

> **第 1 批全部在 PC 上完成，一行硬件代码都不用写。** 这一步做完，项目的"地基"就有了，后面每加一块都是往上贴。

### 7.3 一次只改一个块的纪律

| 规则 | 说明 |
|---|---|
| 一个 commit 只动一个模块 | 出问题 `git revert` 精准 |
| 改公共头文件要单独 commit | 影响面最大，必须能单独回滚 |
| 改协议/引脚要打 tag | 前后端必须同步升级 |
| 集成失败先怀疑最后一个改动 | 二分定位 |

## 8. 变更管理

### 8.1 三个"冻结区"

| 冻结区 | 文件 | 变更要求 |
|---|---|---|
| **引脚** | `board_pinmap.h` | 改一次要重测接线，需记录到设备文档 |
| **协议** | `00` §5 帧 ID 表 | 加字段可以，改语义必须升版本号 |
| **模块接口** | `include/*.h` | 改签名要同步改所有调用方 + 单测 |

### 8.2 版本号规则

```
固件版本：MAJOR.MINOR.PATCH
  MAJOR：协议不兼容
  MINOR：加功能但协议兼容
  PATCH：修 bug

每块板独立版本：B1-v1.2.3 / B2-v1.0.5 / B3-v1.0.2
上位机独立版本：GW-v0.3.1
```

**心跳帧里带版本号**（`0x13` 已有），上位机启动时校验三块板版本是否匹配，不匹配就告警。

### 8.3 OTA 的三条规矩

1. **一次只升一块板**，升完校验版本再下一块。
2. **升级前先记录旧版本**，失败能回滚。
3. **升级过程中禁止运动**（`sys` 进入 OTA 状态，电机强制停）。

## 9. 代码审查清单（每次 AI 生成后逐条过）

> 这份清单直接贴给 AI 当约束，也用于人工复核。

### 9.1 结构

- [ ] 这个模块只做一件事？名字能准确描述它？
- [ ] 公共头文件里没有 `Arduino.h` / `driver/` / `WiFi.h`（算法层）
- [ ] 没有横向调用同层模块
- [ ] 引脚号都是从 `board_pinmap.h` 取的，没有硬编码数字
- [ ] 没有跨模块直接读 `g_xxx`

### 9.2 运行

- [ ] `init` 失败不会阻塞其他模块
- [ ] `stop()` 会把输出置于安全状态
- [ ] 任务栈够用（一般 4096，含浮点/JSON 的给 8192）
- [ ] 中断里没有 `malloc`、没有 `delay`、没有浮点
- [ ] 队列用 `xQueueOverwrite`，不会阻塞生产者
- [ ] 所有 `while` 等待都有超时

### 9.3 健壮性

- [ ] 数组访问都有边界检查（尤其解析外部数据）
- [ ] 除法都防了除零
- [ ] 浮点比较用区间，不用 `==`
- [ ] 协议解析遇到坏帧能跳过，不卡死
- [ ] 长度字段来自外部时做了上限校验

### 9.4 可测

- [ ] 纯算法部分能脱离硬件编译
- [ ] 有对应的单测（或至少能构造输入输出）
- [ ] 有 `examples/ex_xxx` 能单独跑

## 10. 常见反模式（见到就打回）

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| `mod_ui` 里 `#include "mod_mtr.h"` 直接读速度 | 横向耦合，UI 和电机绑死 | 通过 `sys` 提供的 `g_ui_data` |
| 在中断里 `Serial.printf` | 阻塞，丢中断，看门狗复位 | 置标志位，任务里打印 |
| 一个 `main.cpp` 写 2000 行 | 无法隔离，改一处崩全局 | 拆到 `lib/mod_*` |
| 全局 `int speed` 到处读写 | 竞态，且不知道谁改的 | 队列 + 快照 |
| 解析函数里 `while(1)` 等一个字节 | 一个坏帧卡死整个任务 | 状态机 + 超时 |
| 所有模块共用一个任务 | 一个模块阻塞全挂 | 按 §3.1 划分 |
| `delay(1000)` 做延时 | 阻塞任务，浪费 CPU | `vTaskDelay()` |
| 直接 `#define LED_PIN 48` 散落各处 | 改板子要全局搜 | 只在 `board_pinmap.h` |
| 用 `String` 拼接协议帧 | 堆碎片，长时间运行必崩 | 定长 `uint8_t buf[]` |

## 12. 这份规范怎么"贯彻到底"

| 场景 | 怎么用 |
|---|---|
| 写 spec | 每个 spec 只描述一个模块，模板照 §7.1 |
| 让 AI 生成代码 | 把 §9 清单 + §10 反模式**原样贴进 prompt** |
| 代码合并前 | 跑 §11 检查表 |
| 联调出问题 | 先查降级矩阵，确认是哪个模块，再看该模块的 `is_healthy()` |
| 加新功能 | 新建一个 `lib/mod_xxx/`，走完 §7.1 六步，**不改老模块** |

> 最后一句是整份文档的精髓：**加功能靠"加模块"，不靠"改老模块"。** 只要守住这条，项目就不会越做越烂。
